# Prompt: Implement SRS 4.2.3 - Pause, Resume, and Cancel Food Listings

Implement Donor lifecycle controls for active food listings: pause, resume, and cancel. Keep the logic in the Donation module and follow route -> controller -> service -> repository -> model.

## Flow

1. Donor calls `PATCH /api/donor/food-listings/:id/status`.
2. Controller reads `donorProfileId` from auth context and receives the requested status.
3. Service verifies that the listing belongs to the donor and checks the status transition.
4. Repository updates the listing status using `findOneAndUpdate`.
5. If the new status is `Cancelled`, service also cancels all active reservations for that listing.
6. Controller returns the updated listing DTO.

## Mechanism

Use the existing `DonationStatus` values:

- `Active`
- `Paused`
- `PendingCancellation`
- `Cancelled`
- `SoldOut`

Business rules:

- `Paused` listings do not accept new reservations.
- `Cancelled` listings do not accept new reservations.
- Pausing does not touch existing reservations.
- Cancelling automatically cancels active reservations tied to the listing.
- Closed listings such as `Cancelled` and `SoldOut` cannot return to normal donor editing flow unless explicitly allowed.

## Algorithm

Use a transition table instead of scattered `if` statements:

```js
const ALLOWED_STATUS_TRANSITIONS = {
  Active: ["Paused", "Cancelled"],
  Paused: ["Active", "Cancelled"],
  Cancelled: [],
  SoldOut: [],
};
```

For cancellation:

```js
await Donation.findOneAndUpdate(
  { _id: donationId, donorProfileId },
  { $set: { status: "Cancelled", closedAt: new Date() } },
  { new: true, runValidators: true },
);

await Reservation.updateMany(
  { donationId, status: "Reserved" },
  { $set: { status: "CancelledByDonor" } },
);
```

This design keeps the donation status as the source of truth while preserving reservation history instead of deleting reservation records.
