# Prompt: Implement SRS 4.2.4 - Apply Ration on a Food Listing

Implement ration support so a Donor can define the maximum quantity one recipient can reserve from a listing. Use the existing `ration` field on the `Donation` model.

## Flow

1. Donor calls `PATCH /api/donor/food-listings/:id/ration`.
2. Controller reads authenticated `donorProfileId` and requested `ration`.
3. Service checks that the listing exists, belongs to the donor, and is not closed.
4. Service validates that ration is a non-negative number and does not exceed the donation limit or remaining quantity when applicable.
5. Repository updates the listing.
6. Recipient reservation service reads `ration` during reservation validation.

## Mechanism

Ration is a per-recipient cap, not a stock quantity. The listing still uses:

- `donationLimit` as original total quantity.
- `remainingQuantity` as available stock.
- `ration` as maximum reservation quantity per recipient.

Reservation validation should reject a requested quantity when:

- quantity is greater than `remainingQuantity`.
- `ration > 0` and quantity is greater than `ration`.
- recipient already has an active reservation for the same listing.
- listing is paused, cancelled, sold out, closed, or uses `PerRequest`.

## Algorithm

Donor ration update:

```js
if (!Number.isFinite(ration) || ration < 0) throw ValidationError;
if (ration > donationLimit && donationLimit > 0) throw ValidationError;
await Donation.findOneAndUpdate({ _id, donorProfileId }, { $set: { ration } });
```

Recipient reservation validation:

```js
if (listing.ration > 0 && requestedQuantity > listing.ration) {
  throw new ConflictError("Requested quantity exceeds ration limit");
}
```

Then the reservation creation uses an atomic donation update:

```js
Donation.findOneAndUpdate(
  { _id, status: "Active", remainingQuantity: { $gte: requestedQuantity } },
  { $inc: { remainingQuantity: -requestedQuantity } },
  { new: true },
);
```

This keeps ration explainable: it is only a maximum-per-recipient rule, while stock consistency stays protected by the atomic MongoDB update.
